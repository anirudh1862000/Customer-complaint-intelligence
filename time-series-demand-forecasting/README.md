# Time-Series Demand Forecasting — Synthetic Monthly Series

A reproducible forecasting demonstration built to show a leakage-aware, chronological forecasting workflow. The included dataset is generated by the script and is **synthetic**; it is not a real company's sales or inventory history.

## What this demonstrates
- Monthly trend, seasonality and noise in a generated demand series
- Lag and rolling-window features created using past observations only
- Chronological train/validation/test split (no random shuffling)
- Random Forest regression compared with a seasonal-naive baseline
- MAE, RMSE and sMAPE evaluation on a held-out future period
- Forecast and evaluation CSV outputs for inspection

## Run
```bash
python -m venv .venv
# Windows: .venv\\Scripts\\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python src/forecast.py --periods 120 --seed 42
```

Outputs are written to `outputs/`:
- `synthetic_monthly_demand.csv`
- `test_forecasts.csv`
- `metrics.json`

## Method
1. Generate a synthetic monthly demand series with trend, annual seasonality and random noise.
2. Build lag features (1, 2, 3, 6 and 12 months) and a 3-month rolling mean shifted by one month.
3. Reserve the earliest 70% for training, the next 15% for validation and the latest 15% for testing.
4. Fit a Random Forest on the training period and compare it with a seasonal-naive forecast (value from 12 months earlier).
5. Report error metrics only on the held-out future test period.

## Limitations and interview notes
- Synthetic metrics demonstrate code execution only; they are not evidence of real demand-forecasting performance.
- This is a one-step-ahead supervised demonstration, not a multi-step production replenishment system.
- A real project needs a licensed dataset, documented forecast origin and horizon, calendar/event covariates available at forecast time, rolling-origin backtesting, and comparison with business-relevant baselines.
- Never use random train/test splitting for time-dependent forecasting when it would mix future and past observations.
- Do not report any performance figures on a resume until the code has been run and the generated outputs have been checked.
